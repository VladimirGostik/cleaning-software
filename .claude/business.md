## Use-cases (Platform skeleton — Phase 1)

### Platform (skeleton)

- **User login** — POST `/login` with email + password + remember flag; validates via Auth::attempt; on success sets session + redirects /dashboard; on fail returns validation error `invalid_credentials`. Session manages is_active flag (future port guard), user locale preference. Logged to Activitylog (login/login_failed/logout events).
- **Forgot password** — GET /forgot-password shows form; POST sends reset link via Mail::queue; link valid 60 min (config/auth.php); user follows to GET /reset-password/{token} + email prepopulated; POST /reset-password updates password via Password::reset.
- **User profile + password change** — GET /profile (no page props, reads shared auth.user) · PUT /profile updates name/email/locale (ProfileService, updates session('locale') + app()->setLocale()) · PUT /profile/password validates current_password via Hash::check, updates password through `ProfileService::changePassword`, which logs out the other mobile phones (see "Use the mobile app").
- **Manage users (CRUD)** — Authorized by policy (viewAny/view/create/update/delete users). QueryBuilder with AllowedFilter search/role/is_active/created_at. Pages Users/{Index,Form}. Create/Edit via useForm (Precognition). Deactivate via is_active toggle (soft revocation, reactivatable). Delete removes user (hard delete, no soft-delete on User model).
- **Manage roles + permissions** — Authorized by policy (viewAny/view/create/update/delete roles; delete blocks SYSTEM_ROLES=['admin']). Pages Roles/{Index,Form}. Form: PermissionManager component to toggle flat permission strings. RoleService::getPermissionsGrouped() groups permissions by resource (2nd word) for UI affordance. No edit of permission catalogue (that is admin-only via PermissionSeeder).
- **View audit log** — Read-only, permission-gated (view audit logs). Pages AuditLogs/{Index,Show}. Lists with filters (subject_type, created_at, causer search). Show renders activity properties + attribute_changes as JSON diff. Activity writers: User/Role LogsActivity, LogAuthenticationActivity (login/logout/login_failed).
- **View media library** — Read-only, permission-gated (view media). Pages Media/{Index,Show}. Displays uploaded files via MediaLibrary. Show page has image preview. No delete yet (future). Mirrors TemporaryUpload lifecycle. Does not list quote, employee or signed-contract files, nor task attachments (those are reached only through their own page).
- **Upload temporary files** — POST /uploads (multipart file) stores in TemporaryUpload (uuid PK, user_id FK, session_id, MediaLibrary collection). Returns 201 {uuid,name,file_name,mime_type,size,url}. DELETE /uploads/{uuid} removes. Consumer forms use uuid validated by OwnedTemporaryMedia rule → service moveToModel($owner, 'collection', $uuid). Cron daily purges TemporaryUpload rows older than 24h.
- **Switch language** — GET /language/{locale} (unauthenticated, full-page reload, no DTO) sets cookie + session locale; redirects back; LocaleMiddleware resolves order: user.locale → session → cookie → Accept-Language → sk. Supports sk/en today (uk will be added on port). App.Enums.SupportedLanguage #[TypeScript].
- **View API documentation** — GET /docs (auth + permission:view api docs) shows Scribe v5 docs. Only api/* endpoints documented. Strategies: GetBodyParamsFromSpatieData, GetResponseFromSpatieData. Covers auth/login, profile endpoints.
- **Navigate app** — Inertia shared nav from NavigationRegistry (BE-driven via #[NavItem] attribute discovery). NavItems on controllers: Dashboard, Users, Roles, AuditLogs, Media, Profile→settings. Icon via NavIconEnum (BE-declared, Material Symbols); invokable controllers (Dashboard/Prehľad) are discovered too. Gated by permission + policy (e.g. Users nav visible only if user can view users). Nav links full-page load (no SPA routing; each click → server round-trip). On port: extend ICONS map for new domains (BuildingOffice2Icon for clients, etc.).
- **View dashboard** — GET / renders Pages/Dashboard.vue (placeholder welcome card, no props; reads shared auth.user.name). On port: add widgets (recent quotes/invoices, upcoming jobs, notifications, team activity).

## Use-cases (Phase 3+ — CleanMaster operational domain, to port)

- **Manage cleaning objects** — Sekretárka (full CRUD) and Vedúca (view) manage physical locations (office/apartment/house/common areas) assigned to each client. Each object holds access info (codes, key box, key count), special instructions, area/floor metadata, and active flag. Deletion is replaced by **deactivation** (is_active=false), preventing future job generation while preserving historical records. Objects are the **central entity** in the quotes → contracts → invoicing chain. **IMPLEMENTED 2026-09-18 (object contacts):** Each object has on-site contact persons (správca/domovník/recepcia, distinct from client's billing contact). Contacts visibility **gated by ViewAllObjects permission** (fail-closed): actors without the permission see the object but no contacts at all (null value on detail, hidden column on list). Write-side gate: gated actors' contact payload ignored on create/update; existing contacts left intact (never wiped). **Billing details of the house (2026-11-01, "Fakturačné údaje"):** an object (apartment house) may carry its own billing identity: name (fakturovaný subjekt), IČO, DIČ, IČ DPH, Peppol ID, billing address. The client stays the managing company. When the billing name is filled, the house is the buyer on every invoice and e-invoice created for that object, and the invoice prints "v zastúpení: <client name>". Without it the client is the buyer, as before. The billing address is all-or-nothing: when none of street, city, postal code is filled, the object's own address is used. Visibility and write rights follow the contacts gate (`ViewAllObjects`): cleaners do not see billing data; gated users' values are ignored on save. Issued invoices never change when the house data changes; drafts take the current data on save. Contact cascade: client delete soft-deletes object contacts in same transaction; object deactivate/reactivate leave contacts untouched (orthogonal, lossless).
- **Create and manage itemized quotes (cenové ponuky)** — **IMPLEMENTED Phase 5, 2026-09-06.** Sekretárka or Vedúca creates price quotes from line-item basis. Two subject modes: linked to a client, or linked to a client + object (work at a specific location). Line items with per-item VAT rate + discount percentage + frequency (quote-only, for phase 7 work-breakdown generation). **No mandatory number** (optional manual field, max 50 chars, unique per tenant); auto-numbering removed (quotes are informal proposals, not tax documents). Issue date + validity period (valid_until) set at creation. Status lifecycle: Draft (editable) → Sent (stamp sent_at, manual action) → Accepted / Rejected / Expired (daily cron checks valid_until past → auto-expire). Lifecycle actions: send (marks Sent + stamps sent_at + dispatches `QuoteSent` event; no customer-facing email phase 5), accept (opens conversion), reject (terminal), duplicate (copy as Draft without number), convertToInvoice (creates Draft invoice with frequency suffix on items, links via quote_id), **convertToContract (IMPLEMENTED Phase 6, reworked 2026-10-31)** (creates Draft service_agreement contract from Accepted itemized quote with client + object, optional service-agreement document template, quote items via the quote item/total blocks, quote_id backlink; the user lands on the contract EDIT page to review the text first). Only Accepted quotes can convert; re-conversion allowed (single quote → multiple invoices/contracts). PDF generation (chrome driver, Blade-based, itemized only). Permission-gated: `view quotes`, `create quotes`, `edit quotes`, `send quotes`, `approve quotes` (accept/reject authority), `delete quotes`, `duplicate quotes` (separate), `convert to invoice`, `create contracts` (separate permissions). VAT recap with per-rate grouping.
- **Create rough quotes without a client (nástrelná ponuka)** — **IMPLEMENTED Phase 5, 2026-09-06.** Sekretárka sends preliminary price quote before client details finalized. Quote created with `client_id` = null + snapshot fields (customer_name required, customer_email/street/city/postal_code optional) instead. Works at any status (Draft/Sent/Accepted). Action `POST /quotes/{id}/attach-client` later attaches client (+ optional object), clears snapshot, marking finalized. Only available while client_id IS NULL. Uses same `edit quotes` permission. Rough quotes sent/accepted while clientless; conversion to invoice allowed (carries snapshot into standalone invoice). Show page displays rough-quote badge (Nástrel) + attach-client panel (ClientOptionData[] + ObjectOptionData[] filtered by client). FE displays customer_name ONLY when client_id IS NULL.
- **Archive document-only quotes** — **IMPLEMENTED Phase 5, 2026-09-06.** Sekretárka uploads pre-existing PDF quote file (e.g., scanned proposal, legacy export) to archive without line items. Quote created with `kind` = document (immutable). Stores the single file on the quote's Document (collection `file`) on the private documents disk. Read-only display in list/show (no edit, items, actions). Download via policy-gated streamDownload. Cannot send/accept/reject/duplicate/convert — terminal archive-only (all lifecycle gates block). Metadata (issue_date, valid_until) for reference only. Subject modes work (client/object/standalone) for archive labeling. Upload via temporary contract (FE /uploads → DTO OwnedTemporaryMedia + TemporaryMediaConstraints → moveToModel to private disk).
- **Create and manage invoices** — Účtovníčka (Accountant) creates invoices (monthly, one-off, special-period types). Three subject modes: linked to a client (bytový podnik), linked to a client + object (work at a location), or standalone with manual customer fields (ad-hoc/nacenenie). **Buyer on invoices (2026-11-01):** when the chosen object has billing details, the house is the buyer (name, IČO, DIČ, IČ DPH, Peppol ID, address) and the invoice shows "v zastúpení: <client>"; the picker shows one line "Odberateľ: <house> · v zastúpení <client>" under the object. Otherwise the client is the buyer. Standalone invoices keep the typed customer. Quotes keep their own buyer. Changing the buyer later never touches an issued invoice; drafts pick up the change on save. The mail recipient stays the form's customer email. At creation, a snapshot of customer/object/supplier data (IČO, DIČ, VAT, address, IBAN, SWIFT) is captured and frozen at issue — Client edits post-issue don't affect invoice display/PDF. **VAT handling:** per-item VAT rate + discount (%) configurable; VAT recapitulation table generated per rate; if non-VAT-payer, VAT rows hidden + PDF prints non-payer clause. **Deposit:** optional prepayment amount; balance due = total − deposit; Pay-by-Square QR encodes balance (not total). **SK-standard compliance:** constant_symbol, specific_symbol, payment_type (transfer/cash/card/cod/other), currency (EUR/CZK/USD, EUR for QR only), rounding mode (none/document/cash005), header+footer text; all snapshot at issue. Tenant defaults for these stored in settings, per-invoice overridable. Per-tenant auto-numbering with manual override, format configurable (`FA-{YYYY}-{XXXX}`, presets + custom). Issue sets `issued_at`, finalizes snapshot (no edits after). **Supplier profile requirement:** invoice cannot be issued until company has complete supplier profile (name, address_line, city, postal_code, ico; plus dic/vat_number when VAT payer). Drafts allowed on incomplete profile. User-facing banner on forms + settings drawer accessible from list header + banner CTA (quick access to complete profile without full-page navigation). PDF templates selectable (Classic/Modern/Minimal Blade views); tenant default stored in settings, overridable per invoice. **Supplier signature & issuer snapshot (Phase 10):** company owner uploads signature/stamp image (PNG/JPG/WebP) in Settings → Fakturácia; signature is stamped on all PDF templates. At issue time, the **signature image is frozen** (if owner later replaces it, re-printed old invoices show the original signature — audit compliance); drafts render the current signature (live preview for "what will be issued"). Footer line shows "Vystavil: {issuer name}" (the person who pressed the issue button), frozen at issue; recurring auto-issued invoices show "Vystavil: Automaticky". Pay-by-Square QR generated when issued + IBAN present + currency=EUR. Email send queued job (up to 3 retries). Lifecycle: Draft (edit/delete allowed) → Issued (immutable snapshot, PDF downloadable) → Overdue (daily cron checks due date) → Paid. **Payments (Oct 2026):** payment is recorded as InvoicePayment rows (date, amount, type, note; partial payments allowed, balance_due = total − deposit − paid); invoice turns Paid when settled and reverts to Issued/Overdue if a payment is deleted. **Bulk actions (Oct 2026):** from the list, issue / send / mark paid up to 100 invoices and download up to 10 as one merged PDF; ineligible items are skipped with a reason. **Exports:** Pohoda XML export for a date range; Peppol/e-invoice (EFA) UBL XML download and submit (no live provider wired yet — default driver is a no-op; mandatory from 2027-01-01 per config). **Invoice email:** per-company subject/body templates with {{invoice.*}} tokens, fallback to built-in text. Clients and the company carry an optional Peppol participant id. Cancel (Issued|Overdue) creates credit note (dobropis) with negated items, own number, linked back to original, **credit note also receives signature + issuer snapshots at cancel time**. **New:** optional link to source quote (quote_id FK) for audit trail when generated from quote.convertToInvoice. Features: variable_symbol derived from number (digits only), delivery_date distinct from issue_date (Slovak law §74), supplier_registration_info (Obchodný zákonník §3a zápis v registri) printed in PDF footer, contact phone + email in pinned page footer. Permission-gated: `view invoices` (Účtovníčka view-only), `create|edit invoices` (Sekretárka + Účtovníčka for full crud), `cancel invoices` (storno/dobropis authority), `ManageBillingSettings` (owner only, signature upload).
- **Create and manage recurring invoice templates** — Vlastník or Účtovníčka creates recurring invoice templates (RecurringInvoice) to auto-generate invoices on a schedule. Frequency (monthly/quarterly/semi-annually/annually) + start date + termination mode (forever / until date / up to N occurrences). Each template has line items (RecurringInvoiceItem) with description/quantity/price/**per-item VAT rate + discount** (no line totals — computed at generation time from current rate + snapshot). **Template-level SK fields:** constant_symbol, payment_type, currency, rounding_mode, header_text, footer_text, deposit; these propagate to each generated invoice (snapshot at generation time). Three subject modes (client-linked/object-linked/standalone) match regular invoices. ## Permissions (Phase 2 — PermissionEnum; 67 cases)

Flat Spatie permission strings, **global catalogue, scoped per tenant via roles** (Spatie teams = `tenant_id`). Format: `<verb> <resource>`. Backed enum: `App\Enums\PermissionEnum` (67 cases, #[TypeScript], methods: label, group, groupLabel, sharedKey, values). ## Authorization model (single axis)

Access = `user/permission axis` only. No plan/feature gating.

- **User/permission axis** — per-tenant Spatie RBAC. Roles bundle permissions; owner customizes per tenant. Example: a Sekretárka with no "edit clients" permission simply cannot. Enforced: BE Policy + `#[Authorize]` + FE `Can` component.
- **Render by capability, not by role.** UI conditionals never check `.roles()` or `.hasRole()`. Always use `Can` component or `useAuthorization().allows(permission)` check. Roles are custom per tenant; capabilities are the contract.

## Domain rules (Phase 2 — Multi-tenancy foundation + Phase 4 invoicing)

1. **Row-level isolation.** Every domain model MUST have `tenant_id` UUID FK + `BelongsToTenant` trait + `TenantScope` global scope (exceptions: User, Tenant, TenantMembership, TenantInterface, Role, Permission, Activity/Media/TemporaryUpload custom scopes). Phase 11 exceptions: global tasks (`tenant_id` NULL, creator-only via `TaskScope`), notifications with no company (nullable `tenant_id`), device tokens and mobile sessions (per person, no company), and task attachments (`media.tenant_id` NULL for personal tasks only, enforced by a DB CHECK; a firm task's files carry the firm's id). Phase 3+ models follow same pattern.
2. **Supplier profile completeness before issue.** An invoice cannot be issued until the company has a complete supplier profile: mandatory name, address_line, city, postal_code, ico (always); plus dic and vat_number when is_vat_payer=true. Drafts are allowed on incomplete profile; only the issue action is gated. New tenant created via "Add company" modal is immediately redirected to Settings→Invoicing to prompt completion (decision D1). Recurring auto-issue (auto_issue=true) generates invoices as Draft + skips issue if supplier incomplete (D2b), advancing the schedule anyway to avoid retry loops. User-facing banner (SupplierIncompleteAlert) appears when supplier incomplete, linking to settings drawer for quick completion.
2. **Team scope discipline.** Spatie Permission teams=true, team_foreign_key=tenant_id. Every role/permission check calls `setPermissionsTeamId(current_tenant_id)` first (middleware, service, test helpers, jobs, console commands). TenantContextMiddleware binds current_tenant_id container, PermissionRegistrar::setPermissionsTeamId(tenant_id).
3. **No cascades (D8).** FKs use `restrictOnDelete()` (prevents accidental cascades) except `invited_by_user_id → nullOnDelete` (inviter may be removed, invitation stays valid). Tenant/User deletion logic: soft-delete Tenant (cascades never fire), deactivate User (is_active=false, never hard-delete globally).
4. **Active membership = authenticated.** Login guards: `is_active=true` AND `hasActiveMembership()`. RequireActiveTenant middleware on all authenticated routes (web logout + redirect / API 403 on zero memberships). Mid-session membership deactivation → next request logs out.
5. **Invitation token (D10).** 64-char random, unique index, 7d expiry, single-use (`accepted_at` nulls out status). Throttle 5/min on POST accept. Plaintext (not hashed; deferred hardening, low-risk internal tool).
6. **No PermissionEnum duplication.** PermissionEnum is global catalogue (67 cases); roles bundle them per-tenant. FE auto-derives can keys from enum (sharedKey = Str::camel, no hand list). useAuthorization().allows(enum) reads page.props.can dynamically (ComputedRef).
7. **Signature snapshot at issue, live for drafts (Phase 10).** Invoice's supplier signature image is frozen at the moment of issue: `invoices.supplier_signature_media_id` captures the tenant's current `signature_media_id`. Draft invoices resolve the tenant's current signature live (FE preview shows "what will be printed"). Issued invoices retain the snapshot forever — if the owner later replaces the signature, reprints of historical invoices render the original image, not the new one. This is audit-compliance by design: the printed document matches the copy the customer received. No signature → no image block in the PDF. Motivation: supplier identity is already frozen on invoices (name, address, IČO, etc.) at issue; signature is part of that identity on a legal document. Storage: Tenant is a HasMedia owner with 'signature' collection (NOT singleFile) on private DOCUMENTS_DISK, so superseded uploads are retained.
8. **Issuer name snapshot from actor, never from request (Phase 10).** Invoice's issuer footer line ("Vystavil: {person}") is stamped from the actor's TenantMembership.display_name (first_name + last_name, fallback to User.name). Recurring auto-issued invoices have "Vystavil: Automaticky" (frozen translation at generation time in app locale). Drafts have no issuer name. Credit notes issued via cancel() also receive issuer + signature snapshots at cancel time. This prevents spoofing: request-supplied issuer names could let any user stamp a colleague's name on an invoice; actor comes from `$request->user()`, guaranteeing identity.
9. **Platform admin owns global content and firm creation (2026-10-31).** `users.is_platform_admin` is a single boolean on the user (not a tenant role, not fillable, never shown to the UI beyond `canCreateTenant`). It gates global document templates and `POST /tenants`. It deviates from the pure RBAC axis on purpose: the owner runs all firms, a tenant permission cannot gate cross-firm data, and an owner email is user-editable. Granted via `app:grant-platform-admin {email}` or by `app:create-owner` when none exists.
10. **A document keeps the text it was created with (2026-10-31).** Template edits (global or firm) never change existing contracts or sent quotes; contracts are frozen on signing (blocks expanded, PDF snapshot stored once); sent quotes freeze at send. A value missing at creation stays as a visible token until the user fills it; signing/sending is blocked while any remain.
11. **Sensitive employee data is fail-closed and minimal (2026-10-31).** Rodné číslo is encrypted at rest, masked on detail, full only on the edit form (audited), absent from logs, lists and queues; employee-subject contract text needs the same permission. Employee files are Admin-only, private, streamed through the app with audit, and permanently deleted on delete. Sample-only template preview ensures real identifiers never pass through the template editor.
12. **Document language is fixed (2026-10-31).** Contract/quote text, token values and document PDF labels render in the configured document locale (default Slovak) regardless of UI, CLI or queue language; invoice PDFs are unaffected.
13. **Buyer rule and billing visibility (2026-11-01).** The buyer of an invoice is the house when the object has billing details (`billing_name` filled), else the client, else the typed standalone customer; the three never mix. The e-invoice endpoint follows the buyer: a Peppol ID on the house (or, for a Slovak buyer, a 10-digit DIČ) routes to the house, and a house with neither is not e-invoice ready (normal invoice, PDF and send still work). Billing data is visible only with `ViewAllObjects` (same gate as contacts), so cleaners and schedule pickers never receive it.

## Critical domain entities (Phase 2)

**Phase 2 foundation (tenancy):**
- `Tenant` — firma/cleaning company. UUIDv7 PK. Columns: owner_id FK → User (restrictOnDelete, D8), name, ico (nullable), country, is_active, soft_deletes. Relations: interface (HasOne TenantInterface), memberships (HasMany TenantMembership), members (BelongsToMany User via TenantMembership). Settings: VAT-payer flag (toggles VAT fields globally), default invoice template + billing fields (Phase 4).
- `TenantMembership` — pivot User × Tenant. UUIDv7 PK. Columns: user_id FK nullable (NULL = employee without app login; restrictOnDelete), employee_type, contact_email, company_name, company_ico, tenant_id FK (restrictOnDelete), is_active (revocation flag, reactivatable), joined_at, first_name/last_name/phone/position (Phase 7 Employees). Unique (user_id, tenant_id). Permission scope for Spatie roles. Relations: user (BelongsTo), tenant (BelongsTo).
- `TenantInterface` — settings per tenant (1:1). UUIDv7 PK. Columns: tenant_id FK unique (restrictOnDelete), color (TenantColorEnum nullable), timestamps. Will add Phase 4: invoice defaults, number format, VAT rate, IBAN, SWIFT.
- `TenantInvitation` — 7d token, single-use, per-tenant. UUIDv7 PK. Columns: tenant_id FK (restrictOnDelete), invited_by_user_id FK (nullOnDelete), email, role_name, token (64 unique), status (InvitationStatusEnum), expires_at, accepted_at, soft_deletes. Partial unique (tenant_id, email) WHERE deleted_at IS NULL AND status='pending'. Relations: tenant (BelongsTo with TenantScope), invitedBy (BelongsTo User).
- `User` — global identity, never soft-deleted (reuse across tenants). UUIDv7 PK. Columns: name, email (unique), password, locale (SupportedLanguage: sk/en/uk), is_active (login guard), email_verified_at, timestamps. Relations: memberships (HasMany TenantMembership), tenants (BelongsToMany via memberships), ownedTenants (HasMany Tenant).
- `Activity` — audit log, custom subclass. UUIDv7 PK. Columns: subject morph (uuid), causer morph (uuid), **tenant_id uuid nullable** (created hook, for login events before tenant bound), created_at. Relations: visibleInTenant scope (tenant_id = ? OR tenant_id IS NULL AND causer is member of ?).
- `Media` — MediaLibrary file storage, custom subclass. Bigint PK (vendor). Columns: model morph (uuid), **tenant_id uuid NOT NULL** except for Task owners, which may be NULL for personal tasks (DB CHECK `media_tenant_required_unless_task`; the hook copies the owner's tenant). Created hook throws if unbound for other owners. Disk, size. Relations: inTenant scope.
- `TemporaryUpload` — staging for moveToModel. UUIDv7 PK. Columns: session_id, user_id FK (nullOnDelete), **tenant_id FK (restrictOnDelete)**, collection, timestamps. TenantScope applied. Relations: user (BelongsTo).
- `Role` — Spatie custom subclass. UUIDv7 PK. Columns: name, guard_name, **tenant_id uuid** (per-tenant roles). Methods: inTenant(tenant_id) scope, isSystem() (= ADMIN_ROLE). Unique (name, guard_name, tenant_id).

**Phase 3+ operational (reserved, not yet ported):**
- `Client` — typ: `Corporate` (firemný — IČO required; DIČ and IČ DPH optional on the client form, owner decision 2026-11-01) or `Private` (private person, IČO optional). The e-invoice card on the invoice detail (`InvoiceEfaCard`) warns when the customer has no valid DIČ or Peppol ID. The client's Peppol ID is the e-invoice endpoint only when the client is the buyer (no billing details on the object). When the object has billing details, the house is the buyer and the house's Peppol ID decides routing (2026-11-01). The buyer needs a Peppol ID, or for a Slovak buyer a 10-digit DIČ (endpoint 0245:DIČ); IČO is never an endpoint. Without one the invoice is not e-invoice ready (no XML, no submit); issue, PDF and ordinary send are unaffected. Has multiple contacts with primary flag. Soft-delete. Partial unique index on (tenant_id, ico) per tenant for active clients.
- `Object` — physical cleaning location (kancelária/byt/dom/spoločné priestory). The **central entity**: client → object → (quote → contract → invoices). Holds access info (codes, keys), special instructions.
- `Quote` (cenová ponuka) — items with name/description/frequency/unit/quantity/price. Status: Draft → Odoslaná → Schválená → Zamietnutá → Expirovaná. Auto-generates work breakdown.
- `DocumentTemplate` (replaces ContractTemplate) — reusable HTML text with `{{key}}` tokens; type (service_agreement/employment/nda/gdpr/other/quote), optional employment type, header/footer flags, active flag. `tenant_id` NULL = global (platform admin); firm override = row with `parent_id` + base snapshot (states base/customized/base_changed); firm-own rows.
